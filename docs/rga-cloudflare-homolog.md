# Cloudflare para o RGA ATS em homologação

**Proposta de endereço.** Usar `ats-homolog.consultoriarga.com.br` como host exclusivo. Adicionar somente o registro desse host quando a origem estiver pronta. Preservar o site, MX, SPF, DKIM e verificações da Resend. Uma origem Cloud Run precisa reconhecer o cabeçalho `Host` e fornecer certificado válido para o nome usado na conexão. Um CNAME para `run.app`, sozinho, não resolve essas condições. Habilitar proxy e **Full (strict)** depois de verificar o certificado na origem. [TLS Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/)

**Opção para restringir a origem.** Um External Application Load Balancer global pode receber HTTPS em IP público e encaminhar pelo Serverless NEG de `us-west1` ao Cloud Run. Ele requer IP, certificado, configuração de frontend e backend, mapa de URLs, política de acesso, logs e manutenção. O preço público de referência dos EUA começa em **US$ 0,025/h** pelo conjunto das primeiras cinco regras globais de encaminhamento, cerca de **US$ 18,25 por 730 horas**, antes de processamento de dados, transferência, Cloud Run e opcionais como Cloud Armor. Conferir preço e volume no projeto antes de provisionar. [Configuração com Serverless NEG](https://docs.cloud.google.com/load-balancing/docs/https/setup-global-ext-https-serverless) · [Preços do balanceador](https://cloud.google.com/load-balancing/pricing)

**Caminhos que podem contornar o WAF.** Com o balanceador e o TLS validados, avaliar `internal-and-cloud-load-balancing` e desabilitar o endereço padrão `run.app` depois de testar cron, webhooks e rotas de revisão. Um balanceador público também pode ser acessado diretamente pelo IP com o host esperado. Se a meta é forçar Cloudflare, avaliar Cloud Armor para restringir o IP de origem da conexão às faixas publicadas pela Cloudflare ou uma forma equivalente de autenticação de origem. Faixas compartilhadas não autenticam, por si só, a zona específica. Validar de uma rede externa a URL padrão, URLs com tag e o IP do balanceador com SNI, além do caminho proxied. [Ingress do Cloud Run](https://docs.cloud.google.com/run/docs/securing/ingress) · [Cloud Armor com Serverless NEG](https://docs.cloud.google.com/armor/docs/integrating-cloud-armor) · [Faixas de IP da Cloudflare](https://www.cloudflare.com/ips/)

**WAF e limites iniciais.** Aplicar somente ao host de homologação. Se o plano permitir, observar os eventos antes de mitigar e separar POSTs de login, cadastro, recuperação de senha, candidatura e solicitação de acompanhamento. Começar pelo tráfego anômalo e usar janelas curtas, com folga para redes compartilhadas e reenvio de formulário. O ATS usa Server Actions, então as submissões podem usar os próprios caminhos `/login`, `/signup`, `/login/recuperar-senha`, `/careers/<org>/<vaga>` e `/careers/<org>/status`. Incluir POST de credenciais do Auth.js sem desafiar o callback OAuth legítimo. Evitar desafios em webhooks, cron autenticado e uploads legítimos. Usar exceções estreitas, manter autenticação ou assinatura existentes e considerar o plano antes de escolher campos e ações na regra. [Limites e disponibilidade das regras WAF](https://developers.cloudflare.com/waf/rate-limiting-rules/)

**Validação antes de restringir a origem.** Conferir login e logout, callback OAuth e cookies, `Host`, `Origin`, redirecionamentos, `AUTH_URL`, links de recuperação e acompanhamento, upload de currículo e webhooks assinados. Confirmar que respostas privadas e páginas de token ficam fora do cache. Verificar que o domínio do ATS funciona pelo proxy e que a origem não responde pelos caminhos externos que deveriam estar bloqueados. Só então ampliar o bloqueio, com um procedimento de reversão acordado.
